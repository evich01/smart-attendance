1. NEW SYSTEM PURPOSE
The current Smart Attendance Checker should be adapted into a company-based employee attendance system.
The system will allow a company to manage employee attendance using QR codes.
There will be three main user roles:
• Admin
• Manager
• Staff
The system should record:
• Employee identity
• Date
• Check-in time
• Check-in status
• Check-out time
• Total working duration
• Attendance session
• Other relevant attendance information
The system should automatically determine whether an employee was Present or Late based on the company's configured attendance rules.

5. TWO DIFFERENT QR CODE SESSIONS
The attendance system should now have TWO separate QR-code processes:
A. CHECK-IN QR CODE
The Manager starts the morning attendance session.
The Manager clicks:
Start Check-In
The backend creates a new Check-In attendance session and generates a unique QR/session token.
The QR code is displayed on the Manager dashboard.
Staff members log into their accounts and scan this QR code.
After a successful scan, the system records:
• Staff ID
• Username
• Employee name
• Date
• Check-in time
• Attendance session ID
• Attendance status
6. CHECK-OUT QR CODE
At the end of the working period, the Manager starts a separate Check-Out session.
The Manager clicks:
Start Check-Out
The backend creates a new Check-Out session with a different unique session token.
The Manager displays the Check-Out QR code.
Staff members scan the Check-Out QR code before leaving.
The system records:
• Staff ID
• Username
• Date
• Check-out time
• Check-out session ID
The system then calculates the employee's working duration.
7. CHECK-IN AND CHECK-OUT MUST BE DIFFERENT
Do NOT use one QR code for both actions.
There should be two distinct session types:
CHECK_IN CHECK_OUT 
For example:
Check-In Session ---------------- type: CHECK_IN date: 2026-09-16 sessionToken: unique-token status: active 
and:
Check-Out Session ----------------- type: CHECK_OUT date: 2026-09-16 sessionToken: different-token status: active 
The backend must validate the QR session type.
A Check-In QR code must NOT be accepted by the Check-Out endpoint.
A Check-Out QR code must NOT be accepted by the Check-In endpoint.
8. ATTENDANCE WORKFLOW
The complete daily workflow should be:
MANAGER | Start Check-In | ↓ CHECK-IN QR | ↓ Staff scans QR | ↓ Backend validates | ↓ Check-in recorded | ┌─────────┴─────────┐ ↓ ↓ Present Late | | └─────────┬─────────┘ | WORKING DAY | ↓ Manager starts Check-Out | ↓ CHECK-OUT QR | ↓ Staff scans QR | ↓ Backend validates | ↓ Check-out recorded | ↓ Working duration calculated 
9. PRESENT / LATE LOGIC
Attendance status should be determined by the backend.
For example, the company may configure:
Work Start Time: 08:00 AM Late Threshold: 08:15 AM 
Then:
08:00 → Present 08:05 → Present 08:15 → Present 08:16 → Late 08:30 → Late 
The exact values must be configurable by Admin.
Do NOT hard-code these values into the frontend.
The backend should calculate the status using the authoritative server/company time.
The frontend should simply display the result returned by the backend.
10. CHECK-IN RULES
A staff member should normally only be able to check in once per working day.
If the same employee scans the Check-In QR code again after already checking in, do not create another attendance record.
Instead return a clear response such as:
You have already checked in today.
The original check-in time must remain unchanged.
11. CHECK-OUT RULES
A staff member should only be able to check out if they have already checked in.
If someone attempts to check out without a check-in record:
You must check in before checking out.
A staff member should normally only be able to check out once.
If they scan again:
Your check-out has already been recorded.
Do not overwrite the original checkout time unless an authorized Admin/Manager explicitly modifies the record.
12. WORKING DURATION
After both check-in and check-out exist, calculate the employee's working duration.
Example:
Check-in: 08:07 AM Check-out: 05:03 PM Working Duration: 8 hours 56 minutes 
The calculation must be performed reliably using backend/server data.
Do not rely on the user's device clock.
If the employee has checked in but has not checked out:
Check-in: 08:07 AM Check-out: — Status: Missing Check-Out 
Do not invent a checkout time.
13. ABSENCE
The system should be able to identify employees who did not check in.
However, do NOT immediately mark an employee absent simply because they have not scanned yet.
While the Check-In session is active, they should remain:
Not Checked In
After the configured attendance cutoff/session closure, the system can identify employees who never checked in as absent.
Example:
Total Staff: 30 Present: 20 Late: 5 Absent: 5 
The exact absence rules should be configurable or clearly defined in the backend.
14. QR CODE SECURITY
The QR codes must be secure and session-based.
Do NOT create a permanent QR code.
Each attendance session should generate a unique token.
For example:
Manager ↓ Start Check-In ↓ Backend creates unique session ↓ Secure token generated ↓ QR code generated ↓ Staff scans ↓ Backend validates token ↓ Attendance recorded 
The backend should verify:
• Token exists.
• Session is valid.
• Session is active.
• Session belongs to the correct date.
• Session is the correct type.
• User is authenticated.
• User has the Staff role.
• Staff member has not already performed that action.
Old QR codes should not be reusable.
Closed sessions should not accept new scans.
15. AUTHENTICATION AND USER IDENTITY
The staff member's identity must come from the authenticated user.
Do NOT allow the frontend to submit an arbitrary username such as:
username: john 
and trust it.
Instead:
Staff logs in ↓ Authentication token ↓ Backend identifies user ↓ User ID obtained from authentication ↓ Attendance associated with that user 
This prevents one employee from submitting attendance on behalf of another employee.
